# StudySpark AI

Paste study notes (or just a topic), get back interactive flashcards and a quiz — generated by an LLM but never rendered as raw chat text. The model returns strict JSON, the backend validates it against a schema, and only validated data ever reaches the UI.

## What this is

A study assistant built for a frontend take-home assignment. The brief: build a small React app that turns free-form text into an AI-generated, structured, interactive tool — not a chatbot — and demonstrate solid handling of everything that goes wrong along the way.

## Architecture

```
studyspark-ai/
  client/                  React + Vite + Tailwind frontend
    src/
      api/studyApi.js       fetch wrapper + typed ApiError
      hooks/
        useGenerateStudySet.js   request lifecycle, cancellation, race-condition guard
      components/
        NotesInput.jsx
        LoadingState.jsx / ErrorState.jsx / EmptyState.jsx
        FlashcardView.jsx / Flashcard.jsx
        QuizView.jsx / QuizQuestion.jsx
        ResultTabs.jsx
      App.jsx

  server/                  Express backend (keeps the API key off the client)
    routes/study.js         POST /api/study/generate
    services/geminiService.js   Gemini REST call, timeout, error mapping
    prompts/studyPrompt.js  system prompt enforcing the JSON contract
    validators/studySetSchema.js  Zod schema + JSON extraction/validation
    index.js                Express app, CORS, rate limiting
```

**Why a backend at all, and not just calling the model from the browser?** Two reasons: the API key can't be shipped to the client, and the model's raw output shouldn't be trusted or exposed directly — the backend is the one place that validates every response before the frontend ever sees it.

**Why plain hooks instead of a state library?** The app has one real async flow (generate → parse → render). `useState`/`useCallback` plus one custom hook (`useGenerateStudySet`) covers that cleanly without pulling in machinery I'd need to explain more than the actual feature.

## AI flow

1. User submits notes → `POST /api/study/generate`
2. Backend sends the notes to Gemini (`gemini-2.5-flash`) with a system prompt that mandates JSON-only output in a fixed shape (see `prompts/studyPrompt.js`), plus `responseMimeType: "application/json"` in the request as a second layer of enforcement at the API level
3. Backend strips any markdown fences / stray text the model might still add, `JSON.parse`s it, then validates the result against a Zod schema (`validators/studySetSchema.js`) — checking types, array lengths, and that every `correctIndex` actually points at a real option
4. Only a validated object is sent back to the frontend; anything that fails validation returns a structured error instead
5. The frontend renders the validated data as flashcards / quiz — it never prints raw model text

## Handling bad AI output (the part that matters most)

| Failure mode | Handling |
|---|---|
| Malformed JSON | Caught by `JSON.parse` try/catch → `422` with a friendly retry prompt |
| Wrong shape / missing fields | Caught by Zod schema, with field-level error details surfaced (collapsed behind a "technical details" disclosure) |
| `correctIndex` out of range | Explicit Zod `.refine()` check, not just "some number" |
| Empty response | Explicit check before parsing |
| Slow response | 30s timeout via `AbortController` on the server-side Anthropic call → `504` |
| Provider `429` / `5xx` | Mapped to distinct error codes and user-facing messages |
| Network failure client-side | Caught in `studyApi.js`, surfaced as `NETWORK_ERROR` |
| User clicks Generate multiple times / stale response overwriting a newer one | `useGenerateStudySet` assigns each request an incrementing id and its own `AbortController`; starting a new request aborts the previous one, and even if a stale response somehow resolves after a newer request started, its result is dropped because the request id no longer matches |
| Model returns valid JSON but says "not enough material" | Explicitly modeled in the prompt/schema (empty arrays + explanatory summary) and rendered as its own state, not an error |

## Setup

**Requirements:** Node 18+, a free Gemini API key from https://aistudio.google.com/apikey (no credit card required).

```bash
# 1. Backend
cd server
cp .env.example .env        # add your GEMINI_API_KEY
npm install
npm run dev                 # http://localhost:3001

# 2. Frontend (separate terminal)
cd client
npm install
npm run dev                 # http://localhost:5173, proxies /api to the backend
```

Open http://localhost:5173, paste some notes, hit Generate.

### Using a different provider

Only `server/services/geminiService.js` talks to the model. To swap providers (Anthropic, Groq, or a local Ollama model), replace the body of `generateStudySet()` with that provider's SDK/fetch call — the rest of the app (prompt, validation, routes, frontend) is provider-agnostic as long as the response still resolves to a text string containing JSON. Smaller/local models are less reliable at strict JSON output, which is exactly what the validation layer in `studySetSchema.js` exists to catch.

## Known limitations

- No persistence — refreshing the page loses the current study set. Session save/reload wasn't implemented in the time available.
- No streaming — the full response is generated server-side before returning, so there's a single loading state rather than progressive rendering.
- Rate limiting is in-memory (`express-rate-limit` defaults) and per-server-instance, not distributed — fine for a single-instance deploy, not for horizontal scaling.
- No automated tests (unit tests for the validator, e.g. asserting malformed/adversarial inputs are rejected, would be the first thing I'd add with more time).
- Bookmarking flashcards is local to the current session only.

## What I'd do next with more time

- Persist sessions (localStorage at minimum, or a lightweight backend store) so a generated set survives a refresh
- Stream the model response and progressively render flashcards as they arrive
- Unit tests around `parseAndValidateStudySet` covering more adversarial inputs
- A refinement loop ("make these harder", "add 5 more questions") that edits the existing set instead of regenerating from scratch

I used Claude to scaffold and iterate on this codebase — including generating first drafts of most files (schema, prompt, hooks, components) and then reviewing/adjusting them for correctness (fixed a dead-code variable in `QuizView.jsx` during review, verified both the client build and server files compile/syntax-check cleanly, hand-tested the validator against valid, markdown-fenced, malformed, and out-of-range inputs, and confirmed the Gemini `generateContent` REST format against current docs before wiring it up). The architecture decisions — backend-side validation as the core requirement, request-id-based race condition handling, the specific error taxonomy — were deliberate choices made for this assignment's grading criteria, not defaults pulled from a template.
